# Windows 1.4.5 列表切换与滚动诊断

本轮把类别切换改为**零位移的视口蒙层淡入**：列表内容、外框、细线、圆角和滚动条都不再参与透明度或位移动画。200 ms 蒙层仍出现 2/5 次超过 20 ms，按既定阶梯缩短为 120 ms；120 ms 组为 1/5 次超过 20 ms。完全硬切时同步筛选刷新本身出现约 32–33 ms 的回调间隔，因此没有采用更差的硬切方案。

这些数字没有完全达到“5 次全部 ≤20 ms”的严格门槛，所以在用户实际确认前，本文只写“已采用更低成本实现”，**不写“卡顿已解决”**。

## 环境指纹

- `renderTier`: 2，**不是 0**，当前探针运行在硬件渲染路径。
- `clientAreaAnimation`: true。
- `dpiScale`: 1.75。
- 探针窗口：1190 × 966 物理像素（680 × 552 DIP）。
- 真实历史只读副本截取为 60 条，其中图片 8 条；源历史和设置未写入。
- 当前视口内启用 `BitmapCache` 的行：6 条。
- 1.4.4 内容宿主：`ScrollContentPresenter`，`ClipToBounds=false`，视口 639.43 × 349.71 DIP，后代范围 639.43 × 445.71 DIP。
- 最终蒙层：`RoundedClipBorder`，大小 639.43 × 349.71 DIP，范围严格等于视口且没有列表子树。

内容宿主的渲染范围确实大于视口，因此“祖先透明会合成比视口更大的列表子树”假设得到部分支持；由于 WPF 回收虚拟化，实测范围不是整份 60 行的总高度，不能把该假设夸大为唯一根因。

探针没有重现用户对 1.4.4 的主观卡顿：旧内容宿主在本机数字反而没有变差。这证明 prompt-38 的 CompositionTarget 回调指标不足以单独验收用户看到的合成卡顿。最终选择阶梯第 3 档，不是因为数字证明它“更快”，而是因为它结构上只合成一个无子元素的视口矩形、完全取消列表位移，并且比 200 ms 少一次超门槛样本；硬切会暴露同步刷新停顿。

## 滚动三组对照

| 场景（均为真实历史副本，5 次） | callback max 中位数 | 相对基线 | UI 延迟 max 中位数 |
| --- | ---: | ---: | ---: |
| HighQuality 缩略图 + 行缓存，1190×966 px（基线） | 19.38 ms | — | 8.56 ms |
| 默认缩略图缩放 | 19.29 ms | -0.09 ms | 5.28 ms |
| 强制关闭行 BitmapCache | 21.04 ms | +1.66 ms | 6.50 ms |
| 放大到 2100×1365 px | 15.49 ms | -3.89 ms | 8.21 ms |

三组分布互相重叠，且放大窗口反而得到更低的 callback 中位数；这与“像素越多必然越慢”相反，说明该回调样本仍被调度时序和缓存命中噪声主导。默认缩放的 UI 延迟指标下降最多（3.28 ms），但 callback 指标只差 0.09 ms，证据不足以修改产品的图片缩放方式。关闭行缓存反而更慢 1.66 ms，也不支持直接删除缓存。本轮按约束没有修改滚动产品逻辑。

## 验收问题

1. `renderTier` 为 2，不是软件渲染 Tier 0。
2. 旧内容宿主后代范围高 445.71 DIP，超过 349.71 DIP 视口；最终蒙层严格等于视口。图层尺寸假设部分成立，但虚拟化限制了实际范围。
3. 同条件下模拟的 1.4.4 行为中位数 16.83 ms，最终 120 ms 蒙层为 17.31 ms；当前探针没有量到改善，不能拿它宣称问题已解决。
4. 最终采用阶梯第 3 档：120 ms 同色视口蒙层。它完全取消位移，不对列表子树做祖先透明动画；第 4 档硬切测得约 32–33 ms，因此未采用。
5. `>33.3 ms` 与停顿均为 0，但“5 次全部 ≤20 ms”未满足（最差 21.20 ms）。需要用户在实际窗口中确认体感。
6. 三组滚动对照差异见上；callback 差异最大的是大窗口组，但方向与假设相反，不能据此修改产品。当前探针测不出用户报告的滚动卡顿。
7. 没有放松或删除任何既有断言。类型筛选测试新增零位移、蒙层单调收敛、无残留层及空结果不播放过渡检查，外框静止断言继续保留。
