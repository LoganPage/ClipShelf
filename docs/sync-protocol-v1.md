# ClipShelf 跨设备同步协议 v1：产品边界

Sync Protocol v1 是 Windows 与 macOS 后续独立实现同步功能时共同使用的兼容性契约。本阶段只交付协议、Schema、Golden Fixtures 和不接入产品运行时的 Windows 参考验证器。

## 冻结的产品规则

- v1 只同步完成配对之后捕获的**新增文字事件**，不回填配对前历史。
- 收到的文字默认只进入本机历史，不自动写入系统剪贴板。
- 删除、清空、撤销和置顶都是本机行为，不产生 v1 同步消息。
- 设置、快捷键、主题、窗口位置和其他设备状态不参与同步。
- 图片、文件和目录继续保留为本机记录；v1 遇到其消息类型必须明确拒绝，不能把路径伪装成文字。
- `eventId` 是事件去重主键。`contentHash` 只用于完整性校验和内容识别，不能代替事件身份。
- `sequence` 按来源设备独立持久化且严格递增；ACK 只能确认没有缺口的连续水位。
- Hello 的协议版本必须全部是大于等于 1 的整数且包含 v1；capability 名称必须唯一。未知但语法合法的 capability 会被保留但不会自动启用。
- 未知可选 JSON 字段在解码时允许并忽略，规范重编码不会保留这些字段；已知字段的语义必须保持不变。
- 错误消息的可选说明最多为 256 个 Unicode 标量值，ASCII、中文和 Emoji 使用相同的标量计数边界；关联消息 UUID 不得为全零。
- 远端 `capturedAtUtc` 不可信，不能单独用于全局排序、冲突解决或安全判断。
- 本阶段没有传输、设备发现、配对或加密。任何产品集成都必须等待安全通道阶段完成，不能直接用明文网络承载 v1 帧。
- Windows 与 macOS 各自保留原生存储模型，绝不直接共享 Windows `history.json` 或 macOS 的历史文件。
- `sync-protocol/v1/fixtures/` 是跨平台兼容性的权威输入；Swift 实现必须逐项得到相同接受、拒绝、Hash、组帧和 ACK 结果。
- 未来 v2 或新 capability 可以扩展图片、文件等能力，但不得改变 v1 已接受消息的含义。

## 与现有产品模型的关系

Windows `ClipItem` 与 macOS `ClipItem` 都包含本机 UI、存储和文件字段。wire event 只映射文字捕获所需的稳定字段，不序列化本机路径、C#/Swift 类型名、置顶状态或本机历史对象。接收端验证并持久化同步状态后，再由各端自己的适配层创建本机文字记录。

本阶段没有修改任何正式产品数据格式，也没有新增 `sync-state.json`。参考 sequence 状态机完全驻留在验证器进程内。

## 下一阶段入口条件

进入安全传输阶段前，macOS 需要实现独立 Swift 编解码器并通过同一份 manifest 与全部 fixtures；还需要单独设计设备身份持久化、认证配对、端到端安全通道、重放保护、限流和状态文件原子写入。只有安全通道完成后，才能接入真实剪贴板捕获和历史导入。
